Providers

One CLI, five targets. Every provider is driven through that host's documented REST API — no provider CLIs installed, and the same commands (up, preview, rollback, list) work everywhere.

local — bundled control plane

The CLI's own hosting: a small HTTP server that stores deploys, keeps aliases, and serves static files. It's what makes previews and rollback trivially available with zero cloud accounts.

Start it

deploy server
# deploy server on http://localhost:8787
#   storage: ./.deploy-storage
#   token:   dev-token

--storage changes where deploys live; --token (or DEPLOY_SERVER_TOKEN) changes the write token; --port changes the port.

Deploy

deploy login
deploy up
#   URL:    http://localhost:8787/<project>/latest/
#   Deploy: http://localhost:8787/<project>/<deployId>/

Rollback & iterate

deploy rollback <deployId> is an instant alias flip — no bytes move. deploy diff and deploy watch work against the local provider out of the box.

Data layout

.deploy-storage/
  registry.json          # projects, deploys, aliases (+ idempotency keys)
  <project>/
    <deployId>/          # one immutable folder per deploy
      index.html
      assets/...
The control plane is a prototype of the hosted service in ARCHITECTURE.md — single process, single storage dir, no auth on reads (the public side), bearer token on writes. For production hosting use a real provider; the CLI targets both with the same commands.

netlify

Deploys through the official Netlify REST API — no Netlify CLI needed.

Setup

  1. Create a Personal Access Token at app.netlify.com → User settings → Applications → Personal access tokens.
  2. Save it: deploy login --provider netlify --token <PAT>

Deploy

deploy up --provider netlify --site my-site
#   URL:    https://my-site.netlify.app
#   Deploy: https://<hash>--my-site.netlify.app

The site is auto-created if it doesn't exist (name from --site, or netlify.site in .deployrc.json, or the project name). Site names are globally unique on *.netlify.app.

How uploads work

  • Production (up): the digest method — the CLI sends the SHA1 of every file, Netlify says which are missing, and only those are uploaded. No zip size caps, no 30-second request limit, deduped across deploys.
  • Previews (deploy preview): branch deploys use the zip method with a branch query param — the documented way to create branch deploys.
  • Override with --method zip|digest.
  • The CLI polls until the deploy is ready (default; --no-wait skips, --timeout <s> bounds it).

Rollback & limits

deploy list --provider netlify          # find the deployId
deploy rollback <deployId> --provider netlify

Uses the restore endpoint — the previous deploy becomes production again. API limits: 3 deploys/min and 100/day per account. Netlify reads _redirects / _headers from the build output.

vercel

Deploys through the Vercel REST API.

Setup

  1. Create a token at vercel.com/account/tokens.
  2. Save it (team id optional, for team-owned projects): deploy login --provider vercel --token <token> or deploy login --provider vercel --token <token> --team <teamId>

Deploy

deploy up --provider vercel
#   URL:    https://<project>.vercel.app
#   Deploy: https://<project>-<hash>.vercel.app

The project is auto-created on first deploy. up sets target: production; preview omits it. The CLI uploads already-built output and tells Vercel not to run its own build.

How uploads work

Every file is uploaded once via POST /v2/files keyed by SHA1 (a 409 means "already uploaded" and is treated as success). The deployment references the shas — no giant base64 request body, and unchanged files between deploys are naturally deduped. The CLI then polls until the deployment is READY before claiming the URL.

Rollback

deploy list --provider vercel           # find the deployment id
deploy rollback <deploymentId> --provider vercel

Uses Vercel's instant-rollback endpoint (the same one the Vercel CLI uses). Preview deployments don't receive the production alias; rollback and list target the project's production line.

cloudflare — Pages

Deploys via the Cloudflare Pages direct upload API.

Setup

  1. Create an API token at dash.cloudflare.com → My Profile → API Tokens with Cloudflare Pages: Edit permission.
  2. You also need your account id (dashboard right sidebar, or any Pages URL).
  3. Save both: deploy login --provider cloudflare --token <token> --account <accountId>

Deploy

deploy up --provider cloudflare
#   URL: https://<hash>.<project>.pages.dev

The project is auto-created on first deploy (production_branch: main).

How uploads work

The current direct-upload contract (same as wrangler): the CLI fetches a short-lived upload JWT, uploads file content keyed by the Pages content hash (only the hashes Pages doesn't already have), then creates the deployment with a manifest JSON field mapping file paths → content hash. The hash is blake3(base64(content) + extension) truncated to 32 hex chars — wrangler's exact hashFile (plain sha256 is rejected at serve time with HTTP 500). The deployment is polled until success (default; --no-wait skips). Asset uploads are authorized by the short-lived JWT, not your API token — the CLI handles this.

Rollback

deploy rollback <id> --provider cloudflare
# ✖ Cloudflare Pages has no rollback API — restore from your dashboard …

Cloudflare Pages has no rollback endpoint, so the command says so clearly. Use the dashboard's rollback UI, or redeploy the previous content. deploy list --provider cloudflare shows deployments and marks the current production.

s3

Deploys static files to an S3 bucket using AWS Signature V4 signing implemented from scratch — no AWS SDK dependency.

Setup

  1. Create an access key with s3:PutObject (and s3:ListBucket) on your bucket. Bucket must have static website hosting enabled for a browser-friendly URL.
  2. Save the credentials: 
    deploy login --provider s3 --access-key <AK> --secret-key <SK> --bucket <name> --region us-east-1
# optional key prefix (default: project name)
deploy login --provider s3 --access-key <AK> --secret-key <SK> --bucket <name> --prefix my-site
    AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY env vars also work.

Deploy

deploy up --provider s3
# → s3://<bucket>/<project>/
#   URL: https://<bucket>.s3.<region>.amazonaws.com/<project>/

Every file is a SigV4-signed PutObject under s3://<bucket>/<prefix>/<path>. If the bucket has website hosting enabled, your real URL is https://<bucket>.s3-website-<region>.amazonaws.com/<prefix>/.

Rollback & list

deploy rollback <id> --provider s3
# ✖ S3 has no built-in rollback — restore from a previous deploy's files …

Plain S3 has no aliases or version pointer, so rollback isn't supported — the command says so clearly. Options: enable S3 versioning and serve through a proxy, or re-upload the previous content. deploy list --provider s3 uses ListObjectsV2.

Security notes

  • Every request (including listings) is SigV4-signed — nothing is public unless your bucket policy says so.
  • Test endpoints via AWS_S3_ENDPOINT (the test suite runs against a mock that recomputes and verifies each signature).
